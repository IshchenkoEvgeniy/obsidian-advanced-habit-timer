# Повторный анализ раздела «Проекты» — 2026-10-02

## Внесённые исправления

После этого анализа внесены изменения по восьми ошибкам ниже:

1. В снимках и редакторе Companion подзадачи получили отдельные ID. Переименование сохраняет исходную строку, метаданные и поддерево; неоднозначное изменение старых данных без ID отклоняется до записи. Отдельные файлы также сохраняют ID пунктов и окружающий текст.
2. Поля Companion согласуются через сравнение предыдущего снимка, текущей локальной задачи и удалённого изменения. Незатронутые удалённо поля сохраняют локальные значения; конфликтующие операции и удаление изменённой задачи останавливаются с ошибкой.
3. Настройки статусов используют общий атомарный путь переименования. Состояние и заметка ищутся по устойчивому ID независимо от префикса `leaf:`/`task:`. Переименование статуса отдельных файлов сохраняет прежнее время завершения.
4. Граница блока учитывает вложенные абзацы и другие элементы, а также ширину табуляции.
5. Checkbox и статус меняются вместе; вложенные чеклисты без этапов используют inline-статусы. Невыполненная строка под заголовком Done больше не считается выполненной только из-за заголовка.
6. Для отдельных файлов сохраняется и читается `completed_at`. При ручном снятии checkbox устаревшее время в метаданных очищается; следующее завершение получает новую дату. Неизвестное историческое время остаётся неизвестным.
7. Каждое окно Projects имеет свой store. Scope, задачи, этапы и статусы публикуются одним снимком после загрузки; переход блокирует редактирование. Компоненты представлений пересоздаются при смене проекта.
8. Native GitHub sync выбирается также по `parentId`, поэтому checkbox-иерархия без этапов не попадает в плоский путь создания draft items.

Дополнительно: ранее связанный вариант статуса, удалённый на GitHub, больше не создаётся автоматически заново. Неиспользуемый промежуточный статус удаляется локально; для используемого, начального или конечного статуса требуется выбрать замену в настройках.

Проверки после правок: `npm run build`, `npm run check` (0 ошибок, 0 предупреждений), `npm run typecheck` в `cloudflare-companion`, `git diff --check` — успешно. Тесты и сценарии в Obsidian не запускались.

Серверные изменения развёрнуты в Worker `habit-timer-companion`, версия `03a1d502-3960-46b7-925a-a1d06928628c`. Новая миграция D1 для этих изменений не требуется. Собран `main.js` в каталоге установленного плагина; для загрузки нового кода нужно перезапустить плагин/Obsidian, для нового редактора Companion — обновить страницу.

Раздел «Ограничения GitHub» ниже описывает отдельные ещё не реализованные возможности; эти исправления не завершают полную двустороннюю синхронизацию названий, перемещения и архива native Issues.

Проверены текущие исходники, включая незакоммиченные исправления: создание и редактирование задач, вложенность, этапы, хранение состояния и заметок, завершение, представления таблицы, синхронизация GitHub и Companion.

Статические проверки выполнены: `npx tsc -noEmit -skipLibCheck` — успешно; `npm run check` — 0 ошибок и 0 предупреждений; `git diff --check` — успешно (только предупреждения Git о преобразовании LF в CRLF).

Тесты не запускались. Ниже приведены сценарии, выведенные из кода, а не воспроизведённые в работающем Obsidian. Данные хранилища, GitHub и Cloudflare не изменялись. Интерфейс в Obsidian и сетевые операции требуют отдельной проверки.

Общая оценка: сохранение идентичности и структура этапов улучшились, но раздел ещё имеет ошибки, способные потерять вложенность, привязку заметки или локальное изменение. Утверждать, что работа с задачами уже полностью унифицирована, нельзя.

## Что улучшено

- Создание и редактирование возвращают файл и физический block ID. Последующий поиск созданной задачи больше не зависит от совпадения введённого и отображаемого названия.
- Старый логический ID сохраняется в метаданных строки при редактировании.
- После редактирования описание сохраняется по обновлённой задаче с block ID.
- Пустые этапы считываются из заголовков источника отдельно от списка задач.
- При неизменённом списке подзадач Companion больше не перестраивает его.
- Есть отдельная обработка переименований статусов GitHub по ID вариантов.
- В календаре учитываются задачи только со сроком, без даты начала.

## Оставшиеся ошибки

### 1. [P1] Companion может удалить потомков при переименовании подзадачи вместе с изменением числа пунктов

Место: `src/services/cloudflare-project-service.ts:118–145`.

Сценарий: у родителя есть дочерняя задача A с вложенным пунктом и задача B. В Companion название A меняют, одновременно добавляя C. У A нет block ID в полученном тексте либо пользователь заменил текст вместе с якорем.

Сопоставление по тексту не находит старую A. Резервное сопоставление по позиции включено только при равном числе подзадач. Вместо A создаётся новая строка; старый фрагмент A, включая её потомков, не попадает в результат. `splice` заменяет весь старый дочерний блок.

Исправление: передавать отдельный неизменяемый ID каждой подзадачи. При неоднозначном сопоставлении останавливать операцию с конфликтом; не удалять старое поддерево как следствие переименования.

### 2. [P1] Изменение одного поля в Companion может затереть другие локальные изменения

Место: `src/services/cloudflare-project-service.ts:83–92`; полный снимок события формируется в `cloudflare-companion/src/project-board.ts:70–87`.

Сценарий: Companion хранит старый снимок. В Obsidian изменили название или срок; в Companion изменили только статус. При применении события `saveTask` получает все старые поля из `incoming`, включая название, срок, приоритет, привычку и оценку. Сравнение с `previous` и локальной задачей выполняется только для подзадач.

Последствие: независимое локальное изменение молча откатывается. Проверка серверной revision не защищает от изменения, которое ещё не отправлено из Obsidian.

Исправление: для каждого поля выполнять сравнение «база — локальное значение — удалённое значение». Применять только изменённые удалённо поля, а одновременные изменения показывать как конфликт. Аналогично проверять удаление против локального изменения.

### 3. [P1] Переименование статуса через настройки всё ещё может потерять привязку заметки

Место: `src/settings/settings-tab.ts:837–844,873`; `src/projects/project-data.ts:155–166`; `src/projects/checklist-state.ts:340,366`.

Сценарий: обычный файловый проект с заголовком `## In Progress`, минимум двумя задачами без сохранённого ID в метаданных и отдельной заметкой у первой. В настройках переименовали статус в Review.

Настройки сохраняют задачи по одной, а `scope.statuses` меняется лишь после цикла. Первая задача перемещается под `## Review`. При обработке следующей задачи `saveTask` загружает источник со старым набором статусов. Заголовок Review временно становится обычным разделом; ключ первой задачи меняется с `leaf:<id>` на `task:<id>`. `reconcile` ищет прежнюю запись только по новому полному ключу и может записать её без `notePath`. Следующая загрузка не восстанавливает утраченную связь автоматически.

Исправление: использовать существующий атомарный `renameStatuses` и для настроек. При смене типа узла искать прежнее состояние по устойчивому ID независимо от префикса `leaf:`/`task:`. Обновление статусов, источника и связей должно составлять одну согласованную операцию.

### 4. [P1] Граница блока задачи обрывается на вложенном абзаце

Место: `src/projects/engine/task-block.ts:1–17`; вызовы при перемещении/удалении/смене статуса в `mutator.ts`, при обновлении детей в Companion.

Сценарий:

```markdown
- [ ] Родитель
  Пояснение к родителю
  - [ ] Дочерняя задача
- [ ] Следующая задача
```

Парсер сохраняет связь дочерней задачи с родителем, но `findTaskBlockEnd` принимает только пустые строки и более глубоко вложенные строки, начинающиеся с `-`. Он останавливается на пояснении.

Последствие: перемещение или удаление родителя оставляет его потомков в прежнем месте; при следующем чтении они могут получить другого родителя. Обработка детей в Companion также работает с неполным блоком.

Исправление: согласовать определение границ с парсером и Markdown-структурой; учитывать абзацы и другие вложенные элементы, а не только маркеры списка.

### 5. [P2] В обычном файловом проекте выполнение и статус могут расходиться

Место: `src/projects/engine/mutator.ts:159–177`; `src/projects/engine/parser.ts:371`; `src/components/projects/ProjectTable.svelte:876–890`.

Сценарии:

- Задача вручную отмечена `[x]` под `## Backlog`. Из таблицы выбирают Backlog. Для источника без этапов и раздела `saveTask` сохраняет старый checkbox; перемещение не выполняется, поскольку нужный заголовок уже Backlog. Парсер снова возвращает Done.
- У задачи под `## Done` снимают checkbox кнопкой таблицы. Строка становится `[ ]`, но статус наследуется от заголовка Done. В интерфейсе задача остаётся выполненной.

Исправление: менять статус и checkbox одним действием через общий метод. Выбрать единый приоритет между checkbox, inline-статусом и заголовком для каждого формата проекта.

### 6. [P2] Время завершения ещё не согласовано между способами выполнения и типами проектов

Место: `src/projects/checklist-state.ts:304,347–348,371–372`; `src/projects/engine/mutator.ts:220–239`; `src/projects/engine/parser.ts:200–222`.

Сценарии:

- Задачу ранее завершили через плагин: дата хранится в метаданных строки. Затем вручную сняли `[x]` в Markdown и загрузили проект, после чего вручную отметили задачу снова. При повторном завершении `reconcile` предпочитает старую дату из метаданных и не записывает новое время.
- В проектах из отдельных файлов сохранение статуса не записывает время завершения во frontmatter; парсер его также не читает. `ChecklistStateStore` для таких проектов сразу возвращает задачи без обработки времени.

Исправление: учитывать переход из невыполненного состояния в выполненное независимо от источника действия. Для отдельных файлов также сохранять и читать `completed_at`; не заменять неизвестное историческое время вымышленной датой.

### 7. [P2] При переключении проекта новый scope публикуется раньше новых задач

Место: `src/projects-view.ts:132–137,164–186`; `src/components/projects/ProjectsApp.svelte:51–71`; `src/components/projects/ProjectTable.svelte:340–410,866–872`.

Сценарий: переключение между проектами с медленной загрузкой. `activeScopeIdStore` уже указывает на B, а глобальные `tasks`, `stages`, `columns` ещё содержат A. Компонент связывает scope B со старым контекстом A и загружает настройки B с признаками старой иерархии. При наличии старых этапов `loadPreferences` может сбросить сортировку нового представления.

Редактирование ещё показанной строки также не заблокировано: оно передаёт старый `task.file` вместе с новым scope и набором статусов. Для ProjectsView есть защита от устаревшего результата загрузки, но она не предотвращает этот промежуточный смешанный интерфейс.

Дополнительно singleton-хранилища общие для всех открытых окон Projects; независимые окна могут перезаписывать контекст друг друга.

Исправление: публиковать scope, задачи, этапы и статусы как один согласованный снимок. На время перехода блокировать редактирование. Держать состояние представления в экземпляре окна; проверять принадлежность задачи проекту перед записью.

### 8. [P2] Вложенные checkbox-задачи без этапов выбирают плоскую синхронизацию GitHub

Место: `src/projects-view.ts:398–408`.

Сценарий: новый файловый проект состоит из родительской checkbox-задачи и вложенных checkbox-подзадач. Нет заголовков «Этап», нумерованных групп и ранее созданных `githubNativeItems`.

Условие выбора native-синхронизации проверяет группы, этапы и уже существующие связи, но не `parentId`/вложенные checkbox. Используется плоский план создания draft items, и локальная вложенность не становится настоящими GitHub Sub-issues.

Исправление: определять потребность в native-синхронизации по реальной иерархии, а не по наличию заголовков и предыдущих связей.

## Ограничения GitHub, которые остаются

Это отдельные незавершённые функции текущей реализации:

- Изменение названия native Issue на GitHub выдаёт предупреждение с предложением вручную изменить Markdown (`projects-view.ts:987–993`).
- Смена родителя на GitHub пропускается; поле этапа при расхождении обновляется из локального значения (`projects-view.ts:977–984,1031–1037`).
- Архивированный связанный native Issue останавливает синхронизацию; локальный архив не согласован с этим путём (`projects-view.ts:923`).
- Удалённый на GitHub вариант статуса может быть создан снова из локального списка: отсутствует согласование удаления определения статуса (`status-options.ts:94–106`).

Таким образом, двустороннее согласование статусов и выполнения уже есть, но полная двусторонняя синхронизация структуры и жизненного цикла задач ещё не реализована.
