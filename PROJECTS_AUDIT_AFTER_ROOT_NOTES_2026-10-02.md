Схема «одна заметка на этап» сокращает число активных файлов и корректно разделяет описания для GitHub. Однако успешная сборка не подтверждает сохранность данных при одновременных изменениях. Найдены 10 проблем; первые четыре имеют высокий приоритет.

## 1. [P1] У старых задач перенос в другой этап может менять ID

Источники: [task-identity.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/engine/task-identity.ts:20), [parser.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/engine/parser.ts:366), [checklist-state.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/checklist-state.ts:130).

Для строк без сохранённого `metadata.id` используется виртуальный ID, зависящий от этапа и номера/текста. При восстановлении состояние ищется среди задач с прежним родителем. Перенос старой строки в другой этап меняет виртуальный ID и родителя; прежняя запись не находится. Для нумерованных строк один только физический block ID также не заменяет виртуальный ID.

Следствия: активная задача может получить пустое описание и новую ссылку, тогда как прежнее описание останется в истории старой заметки. Привязка GitHub по старому ключу также перестаёт соответствовать новой задаче. При повторной синхронизации возможен запрос создания дополнительного Issue вместо обновления существующего. Переименование ненумерованной строки без устойчивого ID вручную имеет похожую проблему.

Исправление: сохранять независимый ID в исходной строке при подключении/миграции задач; для групп и этапов также нужны устойчивые идентификаторы. При изменении формата обновлять привязки по ID, не по расположению. Неоднозначное сопоставление должно требовать разрешения, а не создавать новую задачу молча.

## 2. [P1] При переносе раздела можно удалить более новое описание

Источник: [checklist-notes.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/checklist-notes.ts:143), строки 179–183, 214 и 270–277.

Сценарий по последовательности операций:

1. `descriptions()` читает описание A из прежней заметки.
2. Пользователь меняет его на B.
3. Повторное чтение для `pendingSectionMoves` запоминает B как допустимую удаляемую версию.
4. Новая заметка получает A из ранее прочитанной карты описаний.
5. Очистка проверяет только наличие раздела в новой заметке. B совпадает с версией очереди, поэтому старый раздел с B удаляется.

Защита `vault.process()` проверяет текущую запись целевой заметки, но не согласованность двух снимков исходного описания. Более новый текст B в этом сценарии исчезает из обеих активных заметок.

Исправление: переносить и проверять один снимок исходного раздела. До удаления подтвердить, что новая заметка содержит именно переносимую версию, а исходная не изменилась. При конфликте сохранять обе версии и отменять очистку.

## 3. [P1] Записи в исходный чеклист не сериализованы

Источники: [mutator.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/engine/mutator.ts:115), строки 207, 245–327; [structured-editor.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/structured-editor.ts:13).

Создание, редактирование, перемещение и ряд других действий используют `vault.read()` → изменение массива строк → `vault.modify()`. Общая блокировка `ChecklistStateStore` защищает файл состояния, а не все изменения исходного Markdown.

Два окна Projects либо Projects и Companion могут прочитать один исходный текст. Вторая запись заменяет результат первой. Возможные последствия: пропадает созданная задача, отменяется выполнение или исчезает изменение поля. Локальный `busy` одного компонента не защищает остальные окна и службы.

Исправление: общий механизм записи на файл через `vault.process()` и/или общую очередь. На момент записи заново находить задачу по ID и применять конкретное изменение к актуальному содержимому.

## 4. [P1] GitHub может затереть описание, изменённое во время синхронизации

Источники: [projects-view.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects-view.ts:802), строки 998–1006; [checklist-state.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/checklist-state.ts:437).

Локальные описания считываются в карту до длительного цикла сетевых операций. Если удалённое описание изменилось относительно базы, а локальный снимок ещё равен базе, выполняется безусловный `saveChecklistNodeDescription()`.

Пользователь может успеть изменить раздел после снимка. Метод сохранения прочитает новую локальную версию, но явный override заменит её удалённым текстом без проверки ожидаемого предыдущего описания. Сравнение файла внутри `vault.process()` защищает только от изменения после этого последнего чтения.

Исправление: передавать ожидаемую версию описания и проверять её при сохранении; конфликт не должен перезаписывать свежий текст. Аналогичная проверка нужна при сохранении описания из долго открытого редактора задачи.

## 5. [P2] Внешние ссылки на раздел ломаются при смене этапа

Источник: [checklist-notes.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/checklist-notes.ts:277).

При переносе ID якоря сохраняется, но меняется файл. Общий индекс получает новую ссылку; другие заметки с `[[Старый этап#^pt-...]]` не обновляются. После удаления прежнего раздела эти ссылки не находят блок. То же касается ссылок из описаний других задач.

Исправление: обновлять ссылки на конкретный блок во всём хранилище либо сохранять в старой заметке блок-переадресацию с прежним якорем. Одного неизменного ID блока недостаточно при изменении пути файла.

## 6. [P2] Ошибка неактивного проекта мешает загрузке активного

Источник: [projects-view.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects-view.ts:171), строки 188–189.

Перед публикацией снимка активного проекта статистика боковой панели вызывает `loadTasks()` для всех остальных проектов через `Promise.all()`. Если у неактивного проекта отсутствует общая заметка, повреждён раздел или JSON, его загрузка выбрасывает ошибку. Снимок исправного активного проекта не публикуется.

Дополнительно сбор статистики запускает полноценное согласование состояния и перенос заметок неактивных проектов, а не только чтение счётчиков.

Исправление: публиковать исправный активный проект независимо от статистики остальных. Ошибки отдельных проектов изолировать; счётчики получать из кэша или отдельного чтения без миграции.

## 7. [P2] Добавление подзадачи может перепривязать вложенный текст

Источник: [structured-editor.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/structured-editor.ts:21), строки 51–54.

Место вставки определяется по последней checkbox-строке потомков, а не по концу полного Markdown-блока. Например, новый сосед добавляется между последней дочерней задачей B и её вложенным пояснением или картинкой. После вставки этот текст визуально и структурно относится уже к новой задаче C.

Исправление: использовать определение полной границы поддерева, включая вложенные абзацы, картинки и обычные списки, и рассчитывать границу на актуальном содержимом файла.

## 8. [P2] Заголовки таблицы предлагают сортировку, которая тут же сбрасывается

Источник: [ProjectTable.svelte](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/components/projects/ProjectTable.svelte:227), строки 411, 691 и 1253–1257.

При иерархии реактивный блок принудительно очищает `sortRules`. При загрузке настроек структурированного чеклиста сортировка также очищается. Меню сортировки скрыто, но кнопки заголовков вызывают `toggleSort()` без этой проверки. Пользователь выбирает сортировку, которая сразу отменяется.

Исправление: либо поддержать сортировку соседей внутри одного родителя с сохранением настроек, либо убрать действие сортировки с заголовков для этого режима и объяснить доступный порядок.

## 9. [P2] Создание и редактирование используют разные правила проверки полей

Источники: [project-data.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/project-data.ts:106), строки 191–213; [task-editor.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/projects/modals/task-editor.ts:256).

`createTask()` проверяет статус, формат оценки, метки, имя привычки и соотношение дат. `saveEditedTask()` и inline-редактирование передают значения в `saveTask()` без этих общих проверок. Модальное окно перед отправкой проверяет только непустое название.

Значения, запрещённые при создании, можно сохранить при редактировании. Например, текстовая оценка не соответствует формату, парсер перестаёт учитывать её как длительность; начало оказывается позже срока. Статус и другие поля также имеют разные пути проверки.

Исправление: одна нормализация и проверка данных перед всеми операциями записи, включая UI, GitHub и Companion; создание добавляет только специфические проверки нового файла/родителя.

## 10. [P2] Companion не замечает изменения описания самой удаляемой задачи

Источник: [cloudflare-project-service.ts](L:/Obs/MySecondBrain/.obsidian/plugins/obsidian-habit-timer-main/src/services/cloudflare-project-service.ts:71), строки 32–35 и 72–75.

Перед удалением сравниваются выбранные поля, время, подзадачи и подпись потомков. В `BoardTask` нет описания корневой задачи; подпись поддерева явно исключает саму задачу. Локальное изменение её описания, меток и некоторых других параметров не вызывает конфликт. Удаление из Companion может примениться поверх этих изменений.

Для файлового чеклиста описание сохраняется в истории общей заметки, но активная задача и её актуальное состояние удаляются. Для проекта из отдельных файлов удаляется файл задачи через корзину.

Исправление: включать подпись полного состояния самой задачи и всех потомков в проверку удаления; изменение описания в общей заметке должно влиять на эту подпись.

## Производительность

Сохранение одного описания через `ChecklistStateStore.write()` читает описания всех общих заметок и повторно обходит все корни. Native GitHub импорт вызывает этот метод отдельно для каждого описания. При нескольких сотнях Issues и десятках этапов это означает тысячи чтений заметок и многократную запись полного состояния/индекса. Время выполнения не измерялось; это оценка количества операций по коду.

Улучшение: пакетное сохранение описаний, чтение каждой заметки один раз на операцию, обновление только затронутых корней и одна запись состояния/индекса. Кэш статистики должен исключить согласование всех проектов при каждом изменении одной задачи.

## Ещё не реализованные возможности

- Native GitHub sync не переносит новое удалённое название в Markdown: сообщает о ручной правке (`projects-view.ts:984`).
- Изменённый на GitHub родитель не согласуется с локальной иерархией (`projects-view.ts:970`).
- Архив связанного native Issue останавливает синхронизацию вместо согласования архива (`projects-view.ts:916`).
- Drag-and-drop между этапами в таблице не выполняет перенос: `dropTask()` обрабатывает только статус, приоритет и привычку (`ProjectTable.svelte:1029`). Механизм переноса описаний пока срабатывает после изменения расположения задачи в исходном Markdown, если её ID сохранился.
- Companion не предоставляет редактор описаний; серверный `BoardTask` не содержит это поле.
- Часть подсказок UI ещё говорит об отдельной «заметке задачи», хотя описание теперь хранится в заметке этапа.

## Что уже работает лучше

- В общих заметках есть отдельные редактируемые разделы и ссылки на блоки.
- Для GitHub извлекается только описание конкретной задачи, а не весь файл этапа.
- Повреждённые служебные разделы и пропавшие общие заметки блокируют перезапись пустыми описаниями.
- Старые заметки архивируются после сохранения новых заметок, состояния и индекса.
- Переименование общей заметки через Obsidian обновляет её адрес в состоянии и общем индексе.
- Статические проверки плагина и Worker проходят.

## Порядок исправлений

1. Устойчивые ID старых задач и безопасный перенос описаний/ссылок.
2. Общий механизм записи исходного чеклиста и контроль версии описания при синхронизации.
3. Изоляция ошибок проектов и пакетное обновление заметок.
4. Границы вставки подзадач, единая проверка полей и согласованные кнопки сортировки.
