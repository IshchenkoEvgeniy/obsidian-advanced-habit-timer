# Аудит поддержки изображений в Projects

Дата: 4 октября 2026 года.

Проверены загрузка изображений в редакторе задач, сохранение чеклистов, извлечение Markdown/wiki-вложений, разрешение путей, показ карточек доски и вызовы редактора из других представлений.

Исходники при аудите не изменялись. Команда сборки обновила игнорируемый `main.js`. Сценарии воспроизводились на текущем коде с небольшими mock API Obsidian, без записи вложений в хранилище. Полная проверка интерфейса в запущенном Obsidian не проводилась.

## Приоритетные ошибки

### 1. P1 — сохранение во время загрузки теряет связь с изображением

Код: `src/projects/modals/task-editor.ts:289–294, 330–341`.

`uploadingImage` защищает только повторную загрузку. Кнопка сохранения не ожидает завершения `getAvailablePathForAttachment`, чтения файла и `createBinary`. Описание и обложка обновляются после этих операций, когда задача уже может быть сохранена и окно закрыто.

Воспроизведение: задержать `arrayBuffer()`, начать загрузку, нажать Save, завершить чтение. Результат: сохранены пустые `description` и `cover`; `Assets/new.png` создан; ссылка добавлена только в объект уже закрытого редактора.

Исправление: хранить Promise текущих загрузок, блокировать или откладывать сохранение до их завершения. После начала сохранения блокировать добавление новых вложений. Передавать в сохранение согласованный снимок данных.

### 2. P1 — обычное сохранение удаляет inline-вложения чеклиста

Код: `src/projects/engine/task-identity.ts:69–70`, `src/projects/engine/mutator.ts:167`; новый сбор изображений — `src/projects/engine/parser.ts:361–371`.

Парсер находит изображения в строке задачи. `taskDisplayTitle` превращает ссылки в текст имени, а `saveTask` пересобирает строку из этого имени и полей. Исходные ссылки обратно не записываются.

Воспроизведение на реальных `ProjectParser` и `ProjectMutator`:

```md
- [ ] Demo ![first](Assets/a.png) ![[Assets/b.png]] ^ht-demo
```

До сохранения: два изображения; отображаемое имя — `Demo !first !Assets/b.png`. После сохранения без изменения полей: `images: []`; в Markdown остаётся `Demo !first !Assets/b.png` и служебные метаданные. Первое изображение может остаться как обложка в метаданных, второе теряется как вложение. Бинарные файлы не удаляются, теряются ссылки из задачи.

Это проблема существующего пути сохранения, которую новая поддержка нескольких inline-изображений не закрыла.

Исправление: сохранять исходные embeds отдельно от отображаемого имени и возвращать их при записи. Если переносить изображения в описание, перенос и удаление исходных ссылок должны быть согласованы; нельзя удалять их раньше успешной записи описания.

### 3. P2 — отмена редактирования оставляет новые файлы без ссылок

Код: `src/projects/modals/task-editor.ts:292–294, 351–352`.

Загруженный файл сразу создаётся в vault. Закрытие редактора только очищает DOM. Отмена после загрузки оставляет файл без сохранённой ссылки; отмена во время загрузки также не останавливает последующее создание файла.

Воспроизведение с задержкой чтения: закрыть окно до завершения загрузки. После завершения `Assets/new.png` всё равно создан, хотя задача не сохранялась.

Исправление: привязать новые загрузки к жизненному циклу черновика. Сохранять их при подтверждении задачи либо вести список файлов, созданных именно этим редактором, и обрабатывать отмену. Очистка должна касаться только собственных новых файлов и учитывать наличие других ссылок.

### 4. P2 — заявленная поддержка Markdown покрывает только простые ссылки

Код: `src/projects/image-utils.ts:11–18, 28–40`; похожие выражения дублируются в `src/projects/engine/parser.ts:196–205, 362–370`.

Результаты запуска текущих функций:

| Ввод | Фактический результат |
|---|---|
| `![[Assets/photo.png]]` | Изображение разрешается |
| `![photo](Assets/photo.png "Caption")` | Подпись включается в путь, изображение не находится |
| `![photo](Assets/photo%20(1).png)` | Путь обрывается на первой закрывающей скобке |
| Обложка `![photo](https://example.com/photo.png)` | URL после удаления Markdown-обёртки не проверяется повторно, результат `null` |
| `![photo](<https://example.com/photo.png>)` | После удаления угловых скобок URL не проверяется повторно, результат `null` |
| Wiki-изображение, затем Markdown-изображение | Markdown-изображение перемещается на первое место |
| Embed внутри fenced code | Ошибочно считается настоящим вложением |

Последние два случая могут менять автоматическую обложку. Reference-style изображения также не извлекаются.

Исправление: единый разбор embeds для парсера и доски с сохранением порядка в документе, пропуском кода и корректной обработкой destination/title/экранирования. URL определять после нормализации ссылки. Декодирование Markdown URL и буквальных wiki-путей должно различаться.

### 5. P2 — относительные пути описания разрешаются от неправильной заметки

Код: `src/components/projects/Board.svelte:155–161`; происхождение описания — `src/projects/checklist-state.ts:432–435`.

Доска смешивает обложку, inline-вложения и изображения описания в один массив, затем разрешает их относительно `task.file.path`. Описание чеклиста находится в отдельной заметке `task.notePath` внутри папки `.tasks`.

Воспроизведение с resolver, учитывающим каталог источника: изображение `./local.png` из `Projects/Board.tasks/Task.md` находится при правильном источнике; при переданном доской `Projects/Board.md` возвращается `null`. Если файлы с одинаковым именем существуют в обоих каталогах, возможен показ другой картинки.

Исправление: хранить источник рядом с каждой ссылкой. Обложку и embeds строки задачи разрешать от файла задачи; embeds описания — от `task.notePath || task.file.path`. Общая замена источника для всех изображений тоже будет неправильной.

### 6. P2 — путь для загрузки передаётся только частью представлений

Код: `src/projects/modals/task-editor.ts:54, 292`; вызовы — `ProjectTable.svelte:976–980`, `ProjectCalendar.svelte:68–84`, `ProjectTimeline.svelte:63–72`.

В доске путь существующей задачи передаётся. Таблица, календарь и таймлайн оставляют `sourcePath` пустым. При создании задачи в проекте по папке он пуст и в доске.

По локальной декларации Obsidian API `getAvailablePathForAttachment` размещает файл с учётом связанной заметки и настроек пользователя. Без корректного пути размещение в режиме «рядом с заметкой» зависит от fallback Obsidian и может отличаться при редактировании одной задачи из разных представлений. Конкретный fallback для пустой строки в живом Obsidian не проверялся.

Исправление: задавать контекст загрузки во всех вызовах редактора. Для новых задач определять будущий путь заметки или явную папку вложений до записи бинарных файлов. Для описаний чеклиста учитывать заметку описания.

### 7. P2 — ссылки генерируются без обработки специальных символов имени

Код: `src/projects/modals/task-editor.ts:258`.

Для пути `Assets/demo]]file.png` создаётся `![[Assets/demo]]file.png]]`. Текущий extractor возвращает `Assets/demo`, и ссылка в описании повреждена. Такие квадратные скобки допустимы в имени файла Windows. Первое изображение может маскировать ошибку за счёт обложки с полным путём; следующие вложения исчезнут из списка доски.

Исправление: использовать корректное создание ссылок через Obsidian FileManager с подходящим форматом и экранированием. Если имя нельзя представить wiki-ссылкой, генерировать корректную Markdown-ссылку. Проверять получившуюся ссылку тем же разбором, который используется при отображении.

### 8. P2 — отдельная локальная обложка не переживает переименование файла

Код: `src/projects/modals/task-editor.ts:251`; хранение — `src/projects/engine/mutator.ts:158, 245`.

Выбор через поле обложки сохраняет голый `file.path`, без Markdown-ссылки в описании. Для чеклистов путь дополнительно находится в закодированном JSON-маркере. Обработчик rename в `src/main.ts:81–115` обновляет идентичность задач и пути заметок, но не эти ссылки на изображения.

После переименования старый путь больше не разрешается: воспроизведено на `resolveProjectImage` с обновлённым списком файлов. Если картинка также прикреплена wiki-ссылкой в описание и Obsidian обновит её, доска может показать её как запасное изображение; выбор обложки всё равно остаётся устаревшим. Особенно заметен случай обложки без вложения в описание.

Исправление: обновлять ссылки на обложки при rename/move изображений, включая метаданные чеклистов, либо использовать формат хранения, который корректно участвует в обновлении ссылок Obsidian.

## Функциональные улучшения после исправлений

1. **Список вложений в редакторе:** миниатюра, имя, размер, просмотр, убрать из задачи, назначить обложкой. Удаление связи с задачей и удаление физического файла — отдельные операции: один файл может использоваться в нескольких заметках.
2. **Галерея всех изображений:** кнопки предыдущего/следующего изображения, клавиатура, номер текущего кадра, открытие исходника. Сейчас доска показывает только первые пять изображений; `+N` не открывает остальные, а preview содержит одну картинку.
3. **Пакетное добавление:** несколько файлов в file picker, drag and drop на карточку/редактор, вставка скриншота через Ctrl+V. Нужны очередь, состояние загрузки и понятное сообщение об ошибке конкретного файла.
4. **Явное управление обложкой:** автоматическая первая картинка, выбранное вложение, без обложки. Сейчас очистка поля не скрывает обложку: доска продолжает показывать первое найденное изображение большим.
5. **Выбор кадрирования:** contain/cover и позиция кадра для скриншотов и схем. Текущий `object-fit: cover` обрезает края.
6. **Состояния ошибок:** отсутствующий локальный файл, недоступный URL, неподдерживаемый формат. Сейчас неразрешённые пути пропускаются молча, а сетевой сбой оставляет сломанную картинку.
7. **Миниатюры и кеш:** небольшие превью для карточек с сохранением оригинала для просмотра; кешировать разбор ссылок и обновлять его при изменении описания/файлов.
8. **Проверки регрессий:** сохранение/отмена во время загрузки, сохранение нескольких inline-вложений, подписи и скобки в Markdown, mixed-order embeds, code fences, относительные пути, rename и загрузка из каждого представления.
