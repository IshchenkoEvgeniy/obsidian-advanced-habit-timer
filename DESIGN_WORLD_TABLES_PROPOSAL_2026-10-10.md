# Предложение: основная таблица этапов и отдельные таблицы мира

Дата: 10 октября 2026 года. Исходное предложение архитектуры. Первая версия реализована: [фактические возможности и проверки](DESIGN_WORLD_TABLES_IMPLEMENTATION_2026-10-10.md).

## Что проверено в текущем плагине

- Активный проект: `Factory Farm Dungeon Mining — Checklist`.
- Его источник — `Projects/Factory Farm Dungeon Mining/DEVELOPMENT_CHECKLIST.md`. При чтении найдено 16 заголовков этапов и 289 строк с Markdown-чекбоксами. Это количество исходных строк, а не результат вычисления количества задач в интерфейсе.
- У этого проекта настроено подключение GitHub. Чтение настроек ограничено определениями проекта и типов; токены не выводились. Сетевые операции GitHub не выполнялись.
- Основная таблица сохраняет иерархию этапов, групп и задач; некоторые обычные сортировки/группировки ограничены для сохранения этой структуры.
- `SavedView` описывает фильтры, колонки и порядок отображения одного набора задач. Новый сохранённый вид не создаёт независимую таблицу с собственной схемой.
- Дополнительные колонки проектной таблицы сейчас привязаны к полям GitHub. Схемы записей мира уже существуют отдельно в «Дизайне мира».
- В текущих настройках есть типы «Персонажи», «Предметы», «Локации» и другие. Отдельного типа «Оружие» пока нет.
- Таблица проекта и канбан используют `ProjectDataEngine`. Записи мира сохраняются через `DesignService`. Эти источники не нужно объединять в один формат задач.

## Рекомендуемая модель

**Проект → таблица данных → представление.**

| Уровень | Что определяет | Пример |
| --- | --- | --- |
| Проект | Общую навигацию и связь плана с материалами мира | Factory Farm Dungeon Mining |
| Таблица данных | Собственные записи, тип и набор полей | План разработки, Персонажи, Оружие |
| Представление | Как показывать записи этой таблицы | Все, Проверка баланса, Канбан готовности, Галерея |

Основной план остаётся отдельным источником с этапами и задачами. Каждая таблица мира показывает записи соответствующего типа. В первой версии удобно иметь одну основную таблицу на тип, а нужные подвыборки создавать как виды. Например, «Персонажи: торговцы» и «Персонажи: жители шахт» не требуют копировать персонажей.

Создание двух таблиц с одинаковыми полями не должно автоматически создавать две копии одних записей. В интерфейсе должны быть разные действия: «Новая таблица / тип» и «Новый вид этой таблицы».

## Предлагаемая навигация

В разделе текущего проекта добавить компактный список:

```text
Factory Farm Dungeon Mining

План разработки                  GitHub

Мир игры
  Персонажи
  Оружие
  Предметы
  Локации
  Механики
  Фракции
  + Новая таблица

Доски
  Боевая система
  Экономика
  ...
```

Основной план закреплён первым. Таблицы можно упорядочивать, переименовывать и отмечать избранными. Кнопка GitHub и его индикатор находятся у плана, а не в общей панели всех данных проекта.

Над выбранной таблицей:

```text
Оружие  /  Все оружие
Таблица | Канбан | Галерея
Поиск · Фильтры · Группировка · Сортировка · Поля · Новая запись
```

Выбор «Оружие» меняет набор данных и схему. Выбор «Проверка баланса» меняет только вид той же таблицы. На телефоне список таблиц открывается отдельной панелью; экран постоянно не занят боковым деревом или длинным рядом вкладок.

«Дизайн мира» и раздел «Проекты» могут открывать один и тот же каталог таблиц. Настройки вида и данные едины, при этом выбор строк и текущий поиск остаются независимыми для каждого открытого окна.

## Примеры отдельных схем

| Таблица | Поля | Возможные виды | GitHub Projects |
| --- | --- | --- | --- |
| План разработки | Этап, задача, статус, приоритет, даты, время, подзадачи | Основная таблица, канбан реализации, календарь, временная шкала | Подключён |
| Персонажи | Роль, фракция, локация, уровень, портрет, описание, готовность дизайна | Все персонажи, по фракциям, канбан готовности, галерея портретов | Отключён |
| Оружие | Класс, урон, скорость атаки, тип урона, цена, редкость, изображение, готовность дизайна | Все оружие, баланс, по классам, канбан готовности | Отключён |
| Локации | Биом, опасность, связанные персонажи, референсы, описание | Все локации, по биомам, галерея, канбан готовности | Отключён |

Это предложенные наборы, а не автоматическое добавление обязательных полей. Пользователь выбирает их при создании/настройке типа. DPS, стоимость рецепта и другие вычисляемые показатели лучше вводить отдельным следующим шагом: поля-формулы в схеме мира сейчас отсутствуют.

Оружие разумно выделить в собственный тип, потому что его характеристики отличаются от обычного предмета. Уже созданные записи оружия из «Предметов» можно переносить с сохранением `design_id`, тела заметки, неизвестных полей и ссылок. Выбор записей для переноса должен быть явным.

## Как должна работать таблица мира

- Одна строка соответствует одной существующей записи мира.
- Колонки определяются схемой выбранного типа и видимостью полей в текущем виде.
- Числа редактируются как числа, ссылки на сущности выбираются из подходящих типов, варианты показывают собственные цвета.
- Клик по названию открывает карточку записи с полями и описанием. На телефоне — отдельный экран карточки.
- Для каждой таблицы доступны собственные фильтры, порядок/ширина колонок и сохранённые виды.
- «Новая запись» в «Оружии» создаёт оружие, а не задачу проекта.
- Создание записи в фильтрованном виде по возможности подставляет однозначные значения фильтра; если это невозможно, интерфейс сообщает, что запись не входит в текущий вид.
- Для ссылок «Персонаж → Фракция» хранится идентификатор записи. Переименование фракции обновляет видимые названия без перепривязки.
- Удаление вида не удаляет записи. Удаление таблицы/типа сначала отделяется от удаления её записей: существующие данные нельзя терять из-за скрытия таблицы в навигации.

## Как должен работать канбан мира

Канбан является представлением той же таблицы. Колонки определяются выбранным полем с одним вариантом значения.

Примеры:

- Персонажи по готовности: «Идея», «Описание», «Проверка», «Утверждён».
- Оружие по классу: «Мечи», «Луки», «Посохи».
- Оружие по редкости: «Обычное», «Редкое», «Легендарное».

Перенос карточки меняет соответствующее поле исходной записи. Перенос в «Редкое» меняет редкость; он не отмечает задачу разработки выполненной.

Для пустого значения нужна колонка «Не указано». Неизвестное значение старой записи также должно оставаться видимым, чтобы данные не исчезали из вида после изменения схемы.

Набор полей на карточке настраивается отдельно от колонок таблицы. Для оружия можно показывать урон, цену и редкость, для персонажа — портрет, роль и фракцию. Цветовая метка и изображение выбираются в настройках вида.

При сортировке карточек по полю ручной порядок не должен незаметно перезаписывать её результат. Для ручного порядка нужны собственные позиции в конфигурации вида. Переименование/удаление варианта колонки не должно потерять записи: отображаемые подписи и постоянные значения вариантов нужно разделить.

## Дизайн и реализация — разные состояния

У записи «Меч шахтёра» могут быть:

- собственное состояние дизайна: «Баланс проверен»;
- связанная задача: «Добавить меч в игру»;
- вычисляемый статус реализации этой задачи: «В работе».

В текущем модуле поле `status` отражает задачу чеклиста. Его нужно сохранить как статус реализации и понятно подписать. Для самостоятельного канбана мира добавить отдельное поле выбора, например «Готовность дизайна».

Связь с этапом/задачей необязательна. Персонаж или оружие может существовать без задачи разработки. При наличии связи можно открывать задачу, создавать её по записи и показывать записи, относящиеся к конкретному этапу.

Редактирование игровых характеристик сохраняет Markdown-запись. Редактирование статуса связанной задачи вызывает движок проекта. Автоматического переноса игровых полей в GitHub не происходит.

## Политика синхронизации

В проверенной конфигурации существующий коннектор — GitHub Projects/Issues. Он отличается от резервного копирования vault через обычный Git или синхронизации файлов Obsidian.

Предлагаемая политика:

| Источник | GitHub | Изменение полей |
| --- | --- | --- |
| План разработки | Разрешён для явно выбранной части плана | Через `ProjectDataEngine` |
| Записи мира | Не участвуют | Через `DesignService` |
| Представления на холсте | Самостоятельно не синхронизируются | Меняют только свой источник |

Ограничение должно проверяться в обработчике синхронизации, а не только скрывать кнопку. Синхронизация выбирает источник плана и его привязки; она не сканирует весь каталог проекта в поисках записей мира.

Существующие GitHub-связи и параметры плана сохраняются. Общий обработчик кнопки не переключается автоматически на «Оружие» вместе с активной таблицей. Поля дополнительных таблиц не определяются списком колонок GitHub и доступны без подключения к нему.

Для первой версии рекомендуемый охват — план этапов вместе с его задачами/подзадачами. Отдельно запрошено уточнение пользователя: требуется ли синхронизировать только верхние этапы. До ответа это рекомендация, а не утверждённое изменение текущего поведения. Сужение до верхнего уровня требует отдельного правила обработки уже существующих связей дочерних задач.

## Что взять у Milanote и Miro

Повторно проверена официальная документация на дату отчёта. Аккаунты приложений не тестировались; поддержка зависит от платформы и некоторых тарифов.

**Milanote:** таблицы — объекты холста с типами ячеек и формулами; колонки упорядочивают карточки. Справка ограничивает содержимое таблиц текстом, числами и чекбоксами и указывает отсутствие мобильного редактирования. Для нашего сценария полезны визуальная простота, изображения и колонки, но эти документы не описывают нужную нам базу записей с общей схемой и несколькими связанными видами. [Tables](https://help.milanote.com/en/articles/8584584-tables), [Columns](https://help.milanote.com/en/articles/10478526-columns).

**Miro:** таблицы поддерживают пользовательские поля, выборки и связанные карточки. Полезный принцип — хранить запись отдельно от способа её показа и подключения внешнего источника. У интегрированных записей синхронизируются определённые поля, остальные могут быть местными. [Tables](https://help.miro.com/hc/en-us/articles/22760922335506-Tables).

**Канбан Miro:** переключается к таблице/временной шкале, использует выбранное поле с одним вариантом для колонок, поддерживает дополнительные группировки. Карточки на холсте могут отражать те же записи. Это хороший ориентир для канбана оружия или персонажей. [Kanban](https://help.miro.com/hc/en-us/articles/29188841316114-Kanban).

Наш выбор — модель связанных записей и представлений с интерфейсом, подходящим к игровым типам. Галерея портретов/оружия — дополнительное предложение для нашего сценария, а не заявление о наличии такого вида у обоих конкурентов.

## Хранение и повторное использование кода

1. Существующая схема `DesignType` остаётся основой полей мира. Рендерер таблицы получает динамические определения вместо списка полей задач.
2. Таблица этапов сохраняет собственную иерархию, вычисление прогресса, чеклист и существующую синхронизацию.
3. Общие части интерфейса выделяются постепенно: выбор таблиц/видов, заголовки, ячейки, поиск, фильтры, ширина колонок, меню и карточки.
4. Сохраняющие действия разделены по источнику. Мир не преобразуется в фиктивные задачи проекта.
5. Определения таблиц и видов сохраняются в синхронизируемых файлах vault, а не только в `localStorage`. Схема имеет один основной источник; перенос нынешних схем из настроек в vault требует версионной миграции с сохранением старой конфигурации.
6. Идентификаторы типов, полей и записей не зависят от видимых названий. Для новых вариантов выбора использовать постоянные значения и отдельные отображаемые подписи.
7. Источник проекта привязан явно; выбор таблицы не меняет настройки GitHub. Состояние загрузки защищено от результата предыдущего выбора таблицы.

Если размещать таблицу/канбан на холсте, блок хранит ссылку на таблицу и вид. При малом масштабе показывает краткий предварительный вид; полноценное редактирование открывается отдельно. Режим «только чтение» должен распространяться на действия источника.

Для больших наборов нужны отображение видимых строк, индекс ссылок и пересчёт фильтров при изменении данных. Перемещение/масштабирование доски не должно повторно загружать все заметки или монтировать все таблицы.

## Порядок реализации

1. Добавить каталог таблиц текущего проекта: основной план и таблицы существующих типов мира. Разделить «Новая таблица» и «Новый вид».
2. Реализовать таблицу записей с динамическими полями, единым редактором записи и сохранением текущих Markdown-файлов.
3. Добавить канбан этих же записей по полю выбора и независимое состояние дизайна.
4. Добавить синхронизируемые сохранённые виды, галерею, удобный телефонный интерфейс и связи с этапами.
5. Подключить выбранные виды к холсту через ссылки и предварительный просмотр.
6. Затем добавлять вычисляемые поля, показатели баланса, CSV-импорт и расширенные операции с выборками.

## Сценарии проверки при реализации

- Изменение урона в таблице обновляет запись, канбан и карточку на двух досках.
- Перенос в колонку меняет только выбранное поле и не запускает GitHub.
- Таблицы персонажей и оружия имеют независимые поля, виды и порядок колонок.
- План сохраняет иерархию этапов и текущие операции с задачами.
- Синхронизация плана не включает записи мира, даже если пользователь переключил таблицу во время загрузки.
- Создание/переименование поля и варианта не скрывает старые записи и не ломает ссылки.
- Удаление вида/блока не удаляет исходные записи.
- Перезапуск и второе устройство сохраняют таблицы/виды при настроенной синхронизации файлов.
- Параллельное редактирование не перезаписывает чужие изменения.
- Телефон позволяет открыть запись и сменить вид без постоянной боковой панели и конфликта с жестами доски.

Основной результат первой версии: в одном проекте доступны привычный план разработки и самостоятельные таблицы мира; каждая таблица имеет собственные поля, а её представления используют одни и те же записи.
