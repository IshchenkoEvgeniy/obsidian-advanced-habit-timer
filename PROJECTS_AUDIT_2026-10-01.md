## Ошибки, которые следует исправить первыми

### 1. P1 — Описание может записаться другой задаче

**Места:** `src/projects/project-data.ts:97`, `src/projects/checklist-state.ts:392`.

В проекте с разделами статусов взять старую задачу без block ID, одновременно изменить название, статус и описание. Смена статуса перемещает строку, а сохранение описания получает прежний объект задачи. Поиск состояния допускает совпадение только по старому номеру строки, без проверки названия или идентификатора.

В изолированном воспроизведении описание `New description` записалось задаче `Sibling`; у переименованной задачи оно отсутствовало. Это ошибка привязки данных, а не только отображения.

**Исправление:** после сохранения получать актуальную задачу по устойчивому идентификатору; исключить небезопасный поиск описания только по номеру строки.

### 2. P1 — При переименовании старой задачи теряется связь с её заметкой

**Места:** `src/projects/checklist-state.ts:174`, `src/projects/checklist-state.ts:329`, `src/projects/engine/mutator.ts:108`.

Создать описание для существующего ненумерованного checkbox без физического block ID, затем изменить его название. Редактор добавляет block ID, парсер получает другой ID, а восстановление состояния не находит старую запись по изменившемуся названию.

В воспроизведении файл описания остался на диске, но `notePath` и описание исчезли из задачи и общего индекса. Аналогично могут потеряться связанные сведения из старой записи состояния.

**Исправление:** переносить запись состояния при переходе от виртуального ID к физическому, независимо от изменения названия.

### 3. P1 — Перетаскивание родителя на его подзадачу нарушает этап

**Места:** `src/projects/engine/mutator.ts:21`, `src/components/projects/ProjectTable.svelte:1017`.

Перетащить родительскую задачу перед её собственным ребёнком. Целевая строка находится внутри перемещаемого блока. После удаления блока вычисляется отрицательная позиция вставки; проверка этого случая отсутствует.

В воспроизведении родитель и ребёнок оказались перед заголовком этапа и потеряли принадлежность к нему. Другие перемещения между уровнями также не проверяют совместимость родителей.

**Исправление:** разрешать изменение порядка среди соседей одного родителя; отдельно обрабатывать перенос к другому родителю; запрещать цель внутри собственного поддерева.

### 4. P1 — Companion меняет вложенность даже при сохранении без изменений

**Место:** `src/services/cloudflare-project-service.ts:86`.

Структура: `Parent → Child A → Grandchild`, а рядом с `Child A` находится `Child B`. Сохранение родителя через Companion удаляет строки непосредственных детей и вставляет их подряд, оставляя строки следующих уровней на прежнем месте.

В воспроизведении сохранение полностью неизменённого snapshot перенесло `Grandchild` из `Child A` в `Child B`.

**Исправление:** сохранять полные поддеревья и идентификаторы детей; не переписывать подзадачи, когда они не изменились.

## Остальные подтверждённые проблемы

### 5. P2 — Создание задачи может завершиться ошибкой после записи в файл

**Места:** `src/projects/project-data.ts:158`, `src/projects/engine/parser.ts:316`, `src/projects/engine/parser.ts:354`, `src/projects/engine/task-identity.ts:43`.

После создания задача ищется по точному совпадению исходного названия с отображаемым названием после разбора Markdown. Эти строки могут отличаться.

Воспроизведены три случая:

- название `**Новая задача**` превращается в `Новая задача`;
- метки `игра, код` попадают в название как `#игра #код`, а список меток остаётся пустым;
- привычка `Работа над проектом` разбирается как `Работа`, а `над проектом` добавляется к названию задачи.

Во всех случаях задача уже существует в Markdown, но операция выдаёт `Task was written, but could not be found after refresh`. Описание не сохраняется; повторное нажатие может создать дубликат.

**Исправление:** возвращать созданный ID из операции записи и искать по нему; поддержать Unicode-метки и полные названия привычек; проверять допустимые значения до записи.

### 6. P2 — Переименование статуса на GitHub возвращает старый статус

**Место:** `src/projects/status-options.ts:59`.

Если на GitHub переименовать `In Progress` в `Review`, локальная строка статусов всё ещё содержит `In Progress`. Алгоритм воспринимает это как отсутствующий локальный статус и создаёт его на GitHub заново, затем добавляет `Review` локально.

На изолированном snapshot получились одновременно `In Progress` и `Review` на обеих сторонах.

**Исправление:** хранить соответствие локального статуса GitHub option ID и распознавать переименование по этому ID. Названия не должны служить единственной идентичностью статуса.

### 7. P2 — У новой задачи, сразу созданной в Done, нет времени завершения

**Место:** `src/projects/checklist-state.ts:336`.

Создание корневой задачи сразу со статусом `Done` даёт `[x]`, но первая запись состояния получает `completedAt: null`. Последующие загрузки сохраняют это значение. Воспроизведено.

Отсутствие времени у впервые импортированной старой выполненной задачи допустимо: реальное время неизвестно. Для задачи, созданной сейчас, момент завершения известен.

**Исправление:** передавать время выполнения из явной операции создания/завершения, отличая её от первого чтения исторического чеклиста.

### 8. P2 — Цвет и обложка checkbox-задачи не сохраняются

**Места:** `src/projects/engine/mutator.ts:111`, `src/projects/engine/parser.ts:375`.

Редактор принимает `cover` и `color`, однако ветка сохранения в общем Markdown-чеклисте не записывает их. Парсер берёт цвет проекта и изображения из исходной строки. Воспроизведено: после сохранения `cover.png` и `#ff0000` оба поля отсутствовали у задачи после перезагрузки.

**Исправление:** определить единое место хранения этих полей для checkbox-задач и читать его во всех представлениях и синхронизациях.

### 9. P2 — Пустые этапы исчезают из интерфейса

**Места:** `src/projects/native-checklist.ts:21`, `src/components/projects/ProjectTable.svelte:244`.

Этапы собираются из задач, а не из заголовков файла. Этап без checkbox-задач отсутствует в таблице и списке выбора этапа, даже если его заголовок остаётся в Markdown. После удаления последней задачи также исчезает запись этапа из пересобираемого состояния.

**Исправление:** разбирать и хранить этапы как отдельные сущности, включая пустые.

### 10. P2 — Задача только со сроком не отображается в календаре

**Место:** `src/components/projects/ProjectCalendar.svelte:55`.

`tasksForDay` сразу исключает задачи без `startDate`. Поэтому задача с заполненным сроком `endDate`, но без начала отсутствует в календарной сетке. Дорожная карта такой случай поддерживает как отдельную дату.

**Исправление:** показывать задачу только со сроком в день срока; единообразно обрабатывать даты в календаре и дорожной карте.

## Ограничения синхронизации, которые интерфейс пока не объясняет

- В режиме настоящей иерархии чеклиста изменение названия Issue на GitHub не переносится в Markdown автоматически: выдаётся предупреждение о ручной правке (`src/projects-view.ts:982`).
- Изменение родителя Issue на GitHub не переносится в локальную структуру (`src/projects-view.ts:968`).
- Поле «Этап» в этом режиме записывается из локальной структуры; удалённое изменение может быть перезаписано (`src/projects-view.ts:1024`).
- Локальное архивирование checkbox-задачи не имеет полноценного соответствующего обмена архивным состоянием в ветке `syncNativeChecklist`; архивный связанный item на GitHub останавливает синхронизацию (`src/projects-view.ts:914`).

Эти ограничения отличаются от полноценной двусторонней синхронизации. Нужны явные правила конфликтов и переноса иерархии.
